# ig/ — Prohori conformance profiles

FHIR Shorthand sources for the profiles the registry enforces — and, since
Phase N, a real published Implementation Guide.

**Live site:** https://khalilurrrahmanridoykhan.github.io/prohori-fhir-case-registry/

```
sushi-config.yaml               SUSHI project config (full IG since Phase N — see ig.ini)
ig.ini                          the IG Publisher's own config: which template (Phase N)
input/fsh/ProhoriPatient.fsh    the Patient profile (Phase E)
input/fsh/ProhoriEncounter.fsh  the Encounter profile (Phase N)
input/fsh/ProhoriObservation.fsh the Observation profile, required-bound to Prohori's own ValueSets (Phase K)
input/fsh/ProhoriCondition.fsh  the Condition profile, required-bound to ProhoriDiagnosisValueSet (Phase N)
input/fsh/ProhoriTerminology.fsh CodeSystem / ValueSets / ConceptMap (Phase K, +1 ValueSet in Phase N) — see ../docs/terminology.md
input/fsh/ProhoriCapabilityStatement.fsh  what Prohori.Api implements (Phase N)
input/maps/hl7v2-to-fhir.map    FHIR Mapping Language (Phase L) — declared, not SUSHI-processed; see ../docs/hl7v2-to-fhir.md
input/fsh/ProhoriMeasure.fsh    CQL Library + Measure (Phase M) — see ../docs/measures.md
input/cql/*.cql                 the actual CQL, plain text (also embedded as Library.content) — see ../docs/measures.md
input/fsh/examples.fsh          one coherent example case — Patient/Encounter/Observation/Condition, cross-referenced
input/pagecontent/*.md          narrative pages (Phase N) — Home, Architecture, Phases A-P
input/tests/*.json              expectation fixtures for scripts/validate-ig.sh
fsh-generated/                  GENERATED by SUSHI — gitignored; regenerate before
                                validating or loading the profile
output/                         GENERATED by the IG Publisher — gitignored; the published site
```

## Regenerate the FSH output only (fast, no IG site)

```bash
npm install -g fsh-sushi
cd ig && sushi . --snapshot
```

CI regenerates it in the `IG` job before validating.

## Build the full, published IG (slow — the real HL7 IG Publisher)

```bash
mkdir -p ~/.fhir/ig-publisher
curl -fsSL -o ~/.fhir/ig-publisher/publisher.jar \
  "https://github.com/HL7/fhir-ig-publisher/releases/latest/download/publisher.jar"
gem install jekyll   # the template's final templating pass needs it — see ../docs/publishing-the-ig.md
cd ig && java -jar ~/.fhir/ig-publisher/publisher.jar -ig ig.ini
open output/index.html
```

See [`../docs/publishing-the-ig.md`](../docs/publishing-the-ig.md) — two real
findings from getting this to run (an insecure default template name, and
Jekyll as an undeclared prerequisite), and how CI builds + deploys it.

## Validate

```bash
bash ../scripts/validate-ig.sh          # needs Java 11+ — offline, structural
bash ../scripts/load-terminology.sh     # PUT the terminology resources onto local HAPI
bash ../scripts/verify-terminology.sh   # live $expand / $validate-code / $translate
```

The full IG Publisher build above also validates every example against its
profile as part of the build itself — that's where the plan's "examples must
pass `$validate`" requirement is actually satisfied.

## Profiles

| Profile | Canonical | Constrains |
| :--- | :--- | :--- |
| ProhoriPatient | `https://prohori.health/fhir/StructureDefinition/prohori-patient` | `Patient` — requires a Bangladesh National ID (sliced identifier + digit invariant), `name.family`, `gender`, `birthDate` |
| ProhoriEncounter | `https://prohori.health/fhir/StructureDefinition/prohori-encounter` | `Encounter` — `status`, `class`, `subject`, `period.start` |
| ProhoriObservation | `https://prohori.health/fhir/StructureDefinition/prohori-observation` | `Observation` — `code` and `valueCodeableConcept` required-bound to Prohori's own LOINC/SNOMED ValueSets |
| ProhoriCondition | `https://prohori.health/fhir/StructureDefinition/prohori-condition` | `Condition` — `code` required-bound to `ProhoriDiagnosisValueSet`; `clinicalStatus`, `verificationStatus`, `subject`, `encounter`, `onset[x]`, `recordedDate` |

## CQL, Measure & MeasureReport (Phase M)

| Resource | Id |
| :--- | :--- |
| Library | `prohori-disease-positivity` (CQL embedded as `content[0]`, `text/cql`) |
| Measure | `prohori-disease-positivity-measure` (proportion, stratified by city) |

See [`../docs/measures.md`](../docs/measures.md) — populations are computed
by `MeasureEvaluator.cs`, not a live CQL engine (checked twice; neither local
HAPI nor the offline validator's CQL↔ELM check had one available).

## CapabilityStatement (Phase N)

`prohori-api-capabilitystatement` — what `Prohori.Api` (a write facade, not a
general-purpose FHIR server) actually implements, checked against
`Program.cs`'s real endpoint mappings. See [Architecture](https://khalilurrrahmanridoykhan.github.io/prohori-fhir-case-registry/architecture.html)
on the published site.
